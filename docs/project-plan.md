# Latency Lab — план MVP на 5 дней

**Срок:** 10–14 ноября 2026 года. Даты взяты от вашего плана на 10.11.

**Команда:** Сергей Степин, Егор Знатнов, Александр Билый.

## Что хотим получить

Сделать простой инструмент для Linux: пользователь вводит команду запуска программы, инструмент запускает её, собирает несколько метрик и показывает результат в терминальном интерфейсе с короткими пояснениями.

**Главный objective:** к концу пятого дня иметь рабочую программу, которую можно запустить и показать на защите.

Критерии готовности:

- [ ] Из TUI можно запустить подготовленную тестовую программу.
- [ ] После запуска видны время выполнения и доступные метрики.
- [ ] Рядом с метриками есть понятные объяснения и подсказки, что проверить в коде.
- [ ] Результат сохраняется в JSON.
- [ ] Проект запускается по README.
- [ ] Есть одно подготовленное демо и короткая презентация.

## Что входит в MVP

- Python TUI: ввод команды, запуск, состояние выполнения, экран результата.
- Python-обвязка через `subprocess` для вызова C++ runner.
- C++ runner: запуск исследуемой программы и сбор метрик через `perf_event_open`.
- Возможность указать один логический CPU для запуска — affinity.
- Один запуск программы по нажатию кнопки.
- Простые текстовые пояснения к результатам.
- Сохранение результата в JSON.

Начальные метрики:

| Метрика | Что показываем |
| --- | --- |
| Время выполнения | Сколько занял запуск программы |
| CPU cycles | Количество тактов CPU |
| Instructions | Количество выполненных инструкций |
| Cache misses | Количество промахов кеша |

Если останется время, добавляем context switches, minor/major page faults и branch misses. Аллокации и блокировки оставляем следующей версии: для них нужна отдельная работа.

Недоступную метрику показываем как «недоступна», с причиной, если она известна.

**За пять дней не делаем:** A/B-сравнение, серии экспериментов, сложную статистику, flame graph, нейросетевой анализ, автоматическое исправление кода и поддержку других ОС.

Флаш кешей не включаем в обязательный план. Сначала получаем рабочие измерения. К управлению состоянием кешей возвращаемся, если основной сценарий уже готов.

Формат пояснения можно сделать простым:

> Cache misses — обращения, при которых нужные данные не найдены в измеряемом кеше. Такие промахи могут увеличивать время работы. Для программы с матрицей стоит проверить порядок обхода данных.

Не нужно вычислять «процент задержки из-за кеша». Для MVP достаточно объяснить наблюдение и предложить следующую проверку. По одному числу не объявляем причину доказанной.

## Как работаем каждый день

- В начале дня: 10 минут, каждый говорит, что сегодня делает.
- Если застряли примерно на час: зовём второго участника, а не тратим весь день в одиночку.
- В конце дня: вместе запускаем текущую сборку. Проверяем соединение частей ежедневно.
- На большую задачу сначала делаем минимальный рабочий вариант, потом улучшаем.
- Задача считается готовой, когда она работает в общем проекте и другой участник её проверил.
- Планируем примерно 4–5 часов конкретных задач на человека в день. Остальное время оставляем на обсуждения и исправления.

## Если не успеваем

| Проблема | Что делаем |
| --- | --- |
| Не все счётчики доступны | Показываем доступные и явно подписываем отсутствующие. Не подставляем придуманные значения. |
| Нет аппаратных счётчиков вообще | Сначала ищем доступную Linux-машину. Пока продолжаем запуск, TUI и время выполнения. Без аппаратных данных не обещаем диагностику кеша. |
| Не успеваем дополнительные метрики | Оставляем время, cycles, instructions и cache misses. |
| Не успеваем объяснения | Оставляем короткие описания метрик и одну подсказку для демо с матрицей. |
| Не успеваем улучшить интерфейс | Сохраняем один экран запуска и один экран результата. |
| Демо сломалось перед защитой | Показываем сохранённый результат с подписью и резервное видео. |

## Что показываем на защите

1. Проблема: программа работает медленно, разработчику нужны данные для поиска причины.
2. Архитектура: Python TUI вызывает C++ runner, который запускает программу и собирает метрики.
3. Демо: запускаем подготовленную программу из TUI.
4. Результат: показываем время, метрики, пояснения и сохранённый JSON.
5. Ограничения и развитие: сейчас поддерживается простой Linux-сценарий; далее можно добавить больше метрик и анализ блокировок и аллокаций.
