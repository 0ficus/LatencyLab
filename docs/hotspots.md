# Участки кода: маленький режим профилирования

Обычные измерения по-прежнему делает C++ runner с `MetricsCollector`.
Кнопка **«Участки кода»** открывает отдельный экран: один запуск программы,
топ-5 мест по сэмплам и пять строк исходника вокруг выбранной строки.
Стрелки в таблице переключают участок. Других настроек perf в интерфейсе нет.

[Скриншоты экрана на тестовых данных](screenshots/hotspots/README.md).

## Подготовка на Linux

Нужны `perf` с поддержкой DWARF/строк исходника и `taskset` из util-linux.
На Ubuntu пакеты perf обычно называются `linux-tools-common` и
`linux-tools-$(uname -r)`, на Debian — `linux-perf`.
Установите подходящий пакет для своей системы; команда `perf version`
должна работать. В виртуальной машине аппаратные события могут быть недоступны.

Пересоберите демо с отладочными символами и сохраните исходники:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build -j 2
python3 -m tui --demo matrix-columns --timeout 30
```

Короткие демо могут завершиться раньше, чем наберётся достаточно сэмплов.
Например, в поле команды увеличьте нагрузку до `./build/demo_matrix 512 10 columns`.
Далее нажмите **«Участки кода»**, затем **CPU** или **Cache misses**.
`sample` относится только к обычной серии измерений: профиль запускается один раз.
Поле CPU используется и здесь; пусто — первый CPU из разрешённого affinity.
Кнопка «Стоп», закрытие экрана и таймаут останавливают процесс профилирования и цель.

## Два режима

| Режим | Что собираем | Как читать результат |
| --- | --- | --- |
| CPU | `cpu-clock:u`, частота 99 Гц | Места, где главный поток выполнялся на CPU |
| Cache misses | `cache-misses:u`, период 1000 событий | Места, около которых зафиксированы сэмплы промахов кеша |

Собирается только главный поток целевого процесса в user space, включая загрузчик.
Дочерние процессы и дополнительные потоки не наследуют счётчики.
Affinity устанавливается через `taskset`; TUI остаётся на своих CPU.
Команда разбирается через `shlex.split` и передаётся без shell.
Сначала `perf record` собирает профиль, затем `perf report` разрешает функции и
`файл:строка`. Строки с одинаковой функцией, местом и бинарником объединяются;
в таблице остаются пять мест с наибольшим числом сэмплов.

**Доля — число сэмплов места / число всех полученных сэмплов**, включая библиотеки
и неразрешённые адреса. Пять строк не нормируются до 100%.
Это не процент wall-clock latency и не точное количество промахов.
CPU-профиль не показывает ожидание блокировки или I/O.
Для cache misses возможен skid: IP может указывать на соседнюю инструкцию.
Оптимизация и инлайнинг также влияют на привязку к строкам.
При числе сэмплов меньше 20 экран просит увеличить объём работы — это подсказка,
а не порог статистической достоверности.

Если нет символов или исходник отсутствует по записанному пути, функция/адрес
остаётся в таблице, а вместо кода показывается объяснение.
Неизвестные места не скрываются. Для Python отображается нативный код
интерпретатора, привязка к строкам `.py` не реализована.

При запрете perf, неподдерживаемом событии или ошибке программы экран показывает
ошибку и диагностику, без подмены события или синтетического результата.
Обычный сбор метрик продолжает работать независимо от этой функции.

## ИИ-диагноз (опционально)

Кнопка **«ИИ-диагноз»** на экране профиля отправляет внешнему LLM горячий код
(топ-5 мест с фрагментами исходника) и, если обычная серия уже запущена, её
метрики и выводы из `analyze`. Модель возвращает короткий вердикт, вероятную
причину и 2–3 эксперимента для проверки. Это дополнение к правилам `analysis.py`,
а не замена; обычный диагноз работает и без сети.

По умолчанию используется DeepSeek (OpenAI-совместимый API):

```bash
export DEEPSEEK_API_KEY=...
```

Настраивается переменными окружения:

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `LATENCYLAB_LLM_BASE_URL` | `https://api.deepseek.com` | база OpenAI-совместимого API |
| `LATENCYLAB_LLM_API_KEY` / `DEEPSEEK_API_KEY` | — | ключ; `LATENCYLAB_LLM_API_KEY` приоритетнее |
| `LATENCYLAB_LLM_MODEL` | `deepseek-chat` | имя модели |

**Локально без ключа и без отправки кода наружу** — Ollama:

```bash
ollama pull qwen2.5-coder:7b
export LATENCYLAB_LLM_BASE_URL=http://localhost:11434/v1
export LATENCYLAB_LLM_MODEL=qwen2.5-coder:7b
```

Ключ читается только из переменных окружения, нигде не сохраняется и не попадает
в `results/`. Сам код и метрики передаются настроенному провайдеру; если это
недопустимо — используйте локальную Ollama. При отсутствии ключа или сети кнопка
показывает понятную ошибку и не блокирует приложение.

## Файлы

В `results/profile-<дата>-<id>/` сохраняются:

- `perf.data` — исходный профиль, если запись была успешна;
- `hotspots.json` — команда, CPU, событие, параметры perf, статус, топ-5 и число сэмплов;
- `report.txt`, `report.stderr.txt` — результат и диагностика разрешения символов;
- `target.stdout.txt` и `record.stderr.txt` — stdout цели и общий stderr цели/perf.

Профили не входят в средние обычной серии и не меняют сохранённую базу сравнения.
На Linux с разрешённым perf полный цикл дополнительно проверяется тестом
`test_real_cpu_profile`; в ограниченной среде он пропускается с причиной.

Форматы и параметры: [perf record](https://man7.org/linux/man-pages/man1/perf-record.1.html),
[perf report](https://man7.org/linux/man-pages/man1/perf-report.1.html).
