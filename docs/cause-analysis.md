# Проверяемые гипотезы о задержках

Анализ разделяет наблюдения, качество данных и гипотезы. Он не выдаёт вероятность
причины и не заменяет профилирование. README проекта не изменён.

## Из TUI

1. Запустите базовый вариант, желательно не менее 5 повторов.
2. Нажмите «Запомнить базу». Исходная серия сохранится в памяти до замены базы.
3. Выберите другой вариант. Если самостоятельно проверили одинаковую задачу,
   объём и входные данные, отметьте «Одинаковая задача и данные» перед запуском.
4. Запустите серию. В панели анализа появятся качество, гипотезы и сравнение
   медиан. Команда базы показана под кнопками.

Проверять одинаковую работу нужно отдельно: равенство checksum полезно для
контроля результата, но не гарантирует одинаковые входные данные и объём работы.
Кнопка «Очистить» очищает текущий результат, сохраняя базу. «Запомнить базу»
заменяет её и сбрасывает флаг эквивалентности. Изменение команды также сбрасывает
флаг: для нового варианта нужно новое подтверждение.

Сводка `results/series-*.json` дополнена полем `analysis`. При выбранной базе
сохраняются `baseline_runs`, `equivalent_work_declared` и `comparison`.
Исходные измерения и формат JSON runner не изменены.

## Из CLI

```bash
python3 scripts/analyze.py results/series-candidate.json
python3 scripts/analyze.py results/series-candidate.json --baseline results/series-base.json --equivalent-work
python3 scripts/analyze.py results/series-candidate.json --baseline results/series-base.json --json
```

Обычный анализ группирует файлы по команде, CPU, kernel, scope и mock: wildcard
не объединяет разные демо в одну причину. Для сравнения нужен один вариант и
одна базовая серия. Не передавайте одновременно серию и входящие в неё файлы
отдельных запусков: это одни и те же наблюдения.

## Что проверяется

- Ошибочные и отменённые запуски исключаются.
- Внутри серии должны совпадать команда и условия измерений.
- Минимум для повторяемости: 3 успешных запуска, каждый не короче 10 мс,
  коэффициент вариации wall time не выше 10%. Это эвристические ограничения,
  не тест статистической значимости и не универсальные нормы производительности.
- Для каждого perf-события требуется известный timing и
  `time_running / time_enabled >= 0.8`. Сильный multiplexing остаётся в исходных
  данных, но соответствующее событие не используется как свидетельство причины.
- Отношения считаются в пределах одного запуска, затем усредняются. Нельзя
  делить средние из разных наборов доступных событий.
- Для срабатывания правила признак должен превышать порог хотя бы в 80%
  доступных измерений; количество наблюдений показывается рядом.
- Cache events называются generic cache events: их смысл зависит от CPU/PMU.
  Backend-stall сам по себе не доказывает ожидание памяти. Низкий CPI сам по
  себе не доказывает отсутствие проблемы.
- `task_clock / wall time` относится к главному потоку. CPU time `wait4` не
  подставляется вместо task-clock: у многопоточной цели области учёта различаются.

Гипотеза содержит наблюдения, альтернативные объяснения, недостающие индикаторы
и следующий эксперимент. Сортировка учитывает число поддерживающих признаков,
а не величину несопоставимых процентов. Статус «несколько согласованных признаков»
требует как минимум двух признаков, полного покрытия серии и повторяемости.
При недоступном perf остаются наблюдения о системном CPU time и page faults.

## Сравнение

Между вариантами должны совпадать CPU, kernel и область учёта. Недостающие
метаданные, mock или неоднородная серия останавливают сравнение.
Медианы времени и доступных показателей выводятся отдельно от гипотез.

Поддержка гипотезы о памяти или ветвлениях появляется только если:

- пользователь подтвердил эквивалентность работы;
- обе серии повторяемы;
- относительное изменение медианы времени больше `max(10%, 2*(CV_A+CV_B))`;
- число инструкций доступно во всех запусках и медианы отличаются не более чем
  на 20% (дополнительная проверка, не доказательство эквивалентности);
- изменение cache misses на инструкцию или branch miss rate более 20% и
  направлено так же, как изменение времени; события доступны во всех запусках.

Отношение к нулевой базе не вычисляется. Ни один порог не является вероятностью
или доказательством причинности. Отдельные серии не контролируют частоту CPU,
фон и порядок запуска. Даже совпадение CPU и kernel не доказывает одну и ту же
физическую машину: модель CPU/PMU пока не сохранена. Используйте одну машину и
повторите эксперимент с чередованием A/B. Автоматический чередующийся runner,
сбор scheduler/I/O-трасс и калибровка порогов остаются следующими этапами.

## Проверки

`tests/test_analysis.py` использует явно синтетические данные для проверки
правил, отказа от необоснованных выводов, сравнения и CLI. Они не выдаются за
результаты измерений. TUI-тест проверяет выбор базы и сохранение сравнения на
реально запущенных процессах.

```bash
ctest --test-dir build --output-on-failure
python3 -m unittest discover -s tests -p 'test_*.py' -v
```
