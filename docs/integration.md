# Контракт модуля для runner

Это предложение интерфейса от Егора на 10 ноября. Согласование с другими
участниками команды ещё не проводилось.

```cpp
#include "latency_lab/metrics.hpp"
latency_lab::MetricsCollector collector; // текущий поток
collector.start();
// измеряемая работа
const auto& metrics = collector.stop();
auto json = latency_lab::metrics_json(metrics);
```

Линковка CMake: `target_link_libraries(runner PRIVATE latency_metrics)`.
Сборщик некопируемый и неперемещаемый; один объект — один интервал.
Повторный `start`, преждевременный или повторный `stop` бросают `logic_error`.
Отказы отдельного события отражаются в `Metric`, а не бросают исключение.
Результат `stop()` принадлежит сборщику; скопируйте вектор, если нужен после его
уничтожения. Потокобезопасность одного экземпляра не предоставляется.

## Внешняя команда: схема для второго дня

Конструктор принимает TID: `MetricsCollector(child_pid)`.
Для измерения главного потока дочерней программы runner должен:

1. Закрепить ребёнка за выбранным CPU и заблокировать перед `exec` через pipe.
2. В родителе создать collector с PID ребёнка и вызвать `start()`.
3. Разблокировать ребёнка, выполнить `exec`, дождаться `waitpid`.
4. Вызвать `stop()`, сериализовать метрики рядом с результатом запуска.

Это схема интеграции, пока не end-to-end реализация. События открыты с
`inherit=0`, `cpu=-1`, `exclude_kernel=1`, `exclude_hv=1` и CLOEXEC.
FD принадлежит родителю; exec дочернего процесса его не закрывает.
Метрики охватывают указанный поток и включат пользовательскую работу после
разблокировки до завершения, в том числе загрузчик. Другие потоки и потомки
не учитываются. Нельзя открывать collector с tid=0 в родителе и считать,
что он измеряет ребёнка. Нельзя запускать ребёнка до открытия событий:
для короткой программы измерение будет потеряно.

## JSON v1

Пример полной оболочки — `results/2026-11-10-host.json`; функция `metrics_json`
выдаёт только содержимое поля `metrics`. Полная оболочка probe — диагностический
формат первого дня, ещё не утверждённый протокол общего runner/TUI.

Каждая метрика содержит:

| Поле | Значение |
| --- | --- |
| `status` | `available` или `unavailable` |
| `value` | Масштабированное число или `null` |
| `raw_value` | Исходный uint64 или `null` |
| `unit` | `count` или `ns` |
| `time_enabled_ns` | Время, когда событие включено |
| `time_running_ns` | Время, когда событие реально считалось |
| `errno` | Код ошибки системного вызова, иначе 0 |
| `reason` | Причина недоступности или `null` |

Формула: `value = raw_value * time_enabled_ns / time_running_ns`.
Нулевое `time_running_ns`, короткое чтение или отказ ioctl означают недоступность.
Метрики независимы: включаются и выключаются последовательно, поэтому интервалы
слегка различаются. Их отношения не гарантируют точную одновременность, особенно
на очень короткой работе. Сам тест включает небольшой overhead start/stop.
Не используйте результаты первого дня для строгой оценки IPC.

`elapsed_ns` — монотонное wall time; `resources` — дельты `getrusage(RUSAGE_THREAD)`.
CPU time имеет микросекундные единицы и дискретность учёта ядра; на коротком тесте
может быть нулевым. Эти поля не заменяют аппаратные значения.

## Смысл базовых метрик

- Cycles: такты CPU, учтённые для потока в пользовательском режиме.
- Instructions: завершённые инструкции в той же области учёта.
- Cache misses: обобщённое аппаратное событие промахов кеша; конкретный смысл
  зависит от CPU/PMU. Это не универсальный счётчик всех уровней кеша и не
  процент времени задержки. Сравнивать нужно при одинаковом CPU и настройках.
