# Контракт модуля для runner

Модуль подключён к внешнему runner в `src/runner/process.cpp`.
API `MetricsCollector` сохраняется: один объект измеряет один интервал одного потока.

```cpp
#include "latency_lab/metrics.hpp"
latency_lab::MetricsCollector collector; // текущий поток
collector.start();
// измеряемая работа
const auto& metrics = collector.stop();
auto json = latency_lab::metrics_json(metrics);
```

Линковка CMake: `target_link_libraries(runner PRIVATE latency_metrics)`.
Сборщик некопируемый и неперемещаемый; один объект — один интервал.
Повторный `start`, преждевременный или повторный `stop` бросают `logic_error`.
Отказы отдельного события отражаются в `Metric`, а не бросают исключение.
Результат `stop()` принадлежит сборщику; скопируйте вектор, если нужен после его
уничтожения. Потокобезопасность одного экземпляра не предоставляется.

## Внешняя команда

Конструктор принимает TID: `MetricsCollector(child_pid)`.
Для измерения главного потока дочерней программы runner должен:

1. Закрепить ребёнка за выбранным CPU и заблокировать перед `exec` через pipe.
2. В родителе создать collector с PID ребёнка и вызвать `start()`.
3. Разблокировать ребёнка, выполнить `exec`, дождаться `waitpid`.
4. Вызвать `stop()`, сериализовать метрики рядом с результатом запуска.

Эта схема реализована в `build/runner`, который Python TUI вызывает через subprocess.
Runner сначала пинится сам, затем ребёнок наследует одно-CPU affinity. После настройки
stdout/stderr ребёнок сообщает о готовности через отдельный pipe и ждёт открытия
счётчиков. Поэтому Python TUI не пинится и не попадает в метрики.
События открыты с
`inherit=0`, `cpu=-1`, `exclude_kernel=1`, `exclude_hv=1` и CLOEXEC.
FD принадлежит родителю; exec дочернего процесса его не закрывает.
Метрики охватывают указанный поток и включат пользовательскую работу после
разблокировки до завершения, в том числе загрузчик. Другие потоки и потомки
не учитываются. Нельзя открывать collector с tid=0 в родителе и считать,
что он измеряет ребёнка. Нельзя запускать ребёнка до открытия событий:
для короткой программы измерение будет потеряно.

## JSON v1

`metrics_json` выдаёт только содержимое поля `metrics`. `build/runner` добавляет
`command`, точный `argv`, фактический `cpu`, `affinity_applied`, `exit_code`, `status`,
`error`, `elapsed_ns`, `resources`, stdout/stderr и признаки обрезки вывода.
В stdout runner находится ровно один JSON; вывод цели захватывается в анонимные
файлы и возвращается внутри JSON, максимум по 64 KiB на поток вывода.

Вызов: `runner [--cpu N] [--timeout-ms N] -- program [args...]`.
Python разбирает кавычки через `shlex.split` и передаёт argv без shell.
Статусы: `ok`, `target_error`, `launch_error`, `timeout`, `cancelled`.
Ошибки настройки до запуска цели дают ненулевой код самого runner и сообщение в stderr.

Сохранённые `results/2026-11-10-*.json` остаются историческими результатами probe первого дня.

Каждая метрика содержит:

| Поле | Значение |
| --- | --- |
| `status` | `available` или `unavailable` |
| `value` | Масштабированное число или `null` |
| `raw_value` | Исходный uint64 или `null` |
| `unit` | `count` или `ns` |
| `time_enabled_ns` | Время, когда событие включено |
| `time_running_ns` | Время, когда событие реально считалось |
| `errno` | Код ошибки системного вызова, иначе 0 |
| `reason` | Причина недоступности или `null` |

Формула: `value = raw_value * time_enabled_ns / time_running_ns`.
Нулевое `time_running_ns`, короткое чтение или отказ ioctl означают недоступность.
Метрики независимы: включаются и выключаются последовательно, поэтому интервалы
слегка различаются. Их отношения не гарантируют точную одновременность, особенно
на очень короткой работе. Сам тест включает небольшой overhead start/stop.
Не используйте результаты первого дня для строгой оценки IPC.

У runner `elapsed_ns` — монотонное wall time от разблокировки до завершения цели;
`resources` возвращаются `wait4` для целевого процесса. Это включает запуск программы.
У отдельного `metrics_probe` ресурсы по-прежнему получены как дельты `getrusage(RUSAGE_THREAD)`.
CPU time имеет микросекундные единицы и дискретность учёта ядра; на коротком тесте
может быть нулевым. Эти поля не заменяют аппаратные значения.

## Смысл базовых метрик

- Cycles: такты CPU, учтённые для потока в пользовательском режиме.
- Instructions: завершённые инструкции в той же области учёта.
- Cache misses: обобщённое аппаратное событие промахов кеша; конкретный смысл
  зависит от CPU/PMU. Это не универсальный счётчик всех уровней кеша и не
  процент времени задержки. Сравнивать нужно при одинаковом CPU и настройках.

Сверка с `perf stat` запланирована на 13 ноября, пока не выполнена.

## Расширенные счётчики и диагноз

Кроме базовых, runner открывает `cache_references`, `branch_misses`,
`branches`, `stalled_cycles_backend`, `stalled_cycles_frontend` (аппаратные) и
`context_switches`, `cpu_migrations` (программные). Первые три
(cycles/instructions/cache_misses) остаются базовыми — по ним `metrics_probe`
считает `hardware_counters_available` в строгом режиме. Отдельный счётчик может
быть недоступен на конкретном CPU/VM; это отражается как `unavailable` с причиной.

Производные индикаторы и гипотезы о причинах задержки считает `tui/analysis.py`
(`analyze(outcomes)`). По `results/series-*.json` их печатает
`python3 scripts/analyze.py`. Гипотезы формулируются как предположения с
доказательствами и подсказкой, что проверить; по одному числу вердикт не выносится.

## sample в TUI

`sample` — число отдельных запусков, от 1 до 1000. При авто-CPU первый запуск
выбирает разрешённый CPU, остальные используют этот же номер. Для каждого запуска
сохраняется исходный JSON; сводка содержит `statistics` со средним, минимумом,
максимумом и числом доступных измерений `n`. Ошибочные запуски и недоступные метрики
не превращаются в нули и не участвуют в среднем. При ошибке или отмене серия останавливается.
