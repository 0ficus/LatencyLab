# LatencyLab

LatencyLab помогает разобраться, почему программа работает медленно. Вы указываете бинарник и число запусков, а инструмент собирает метрики, показывает разброс времени и предлагает, что проверить в коде.

Например, можно посмотреть, как меняются время и cache misses при обходе массива подряд или с большим шагом.

## Что уже работает

- Запуск программы с аргументами из терминального интерфейса.
- Закрепление программы за одним ядром CPU.
- Несколько запусков подряд: среднее время, минимум и максимум.
- Сбор циклов CPU, инструкций, промахов кеша и других доступных счётчиков.
- Гипотезы о причинах задержки с пояснениями и подсказками.
- Сохранение результатов в JSON.

Это пока прототип. По метрикам можно найти подозрительное место, но точную причину замедления всё равно нужно проверять.

## Запуск

Нужны Linux, Python 3.11+, компилятор с поддержкой C++17 и CMake 3.16+. Если CMake нет в системе, он установится вместе с Python-зависимостями.

Из корня проекта:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build -j2

python3 -m tui --demo
```

Откроется интерфейс с готовой командой. Можно запустить её или вписать свой бинарник:

```text
./my_program --size 1024
```

В интерфейсе есть два основных поля:

- **CPU** — логическое ядро, на котором будет работать программа. Если оставить пустым, выберется первое разрешённое.
- **sample** — сколько раз запустить программу. Например, `5` означает пять отдельных запусков на одном и том же CPU.

Нажмите **«Запустить»**. Результаты появятся ниже: время, метрики, пояснения и вывод программы. **«Стоп»** прерывает текущий запуск и оставшуюся серию.

По умолчанию на один запуск даётся 10 секунд. Для более долгой задачи можно указать свой таймаут:

```bash
python3 -m tui --demo matrix-columns --timeout 30
```

Результаты сохраняются в папку `results/`: отдельные запуски — в `run-*.json`, сводка серии — в `series-*.json`. В средние значения входят только успешные запуски.

## На чём попробовать

В проекте есть несколько небольших демо:

- обход массива подряд и с большим шагом;
- бинарный поиск;
- умножение матриц с разным порядком обхода.

Демо можно выбрать в интерфейсе или сразу при запуске:

```bash
python3 -m tui --demo array-sequential --sample 5
python3 -m tui --demo array-strided --sample 5
python3 -m tui --demo binary-search
python3 -m tui --demo matrix-rows
python3 -m tui --demo matrix-columns
```

Размер задачи и число проходов меняются прямо в строке команды. Проходы внутри программы и `sample` — разные вещи: первые задают объём работы одного процесса, второе — число его отдельных запусков.

[Параметры всех демо](docs/demos.md)

## Если часть метрик недоступна

Linux или виртуальная машина могут запрещать доступ к счётчикам CPU. В таком случае LatencyLab покажет причину вместо значения. Время выполнения и доступные ресурсные показатели останутся.

Если проблема связана с настройкой `perf_event_paranoid`, в проекте есть скрипт:

```bash
scripts/enable_perf.sh
```

Он покажет предлагаемое изменение и запросит подтверждение. Понадобятся права root или sudo: настройка меняется для всей машины и действует до перезагрузки. В контейнере или VM этого может быть недостаточно.

На macOS можно посмотреть интерфейс с явно выбранным моком, но настоящий C++ runner работает только на Linux. [Как запустить интерфейс с моком](tui/README.md#мок-для-просмотра-интерфейса).

## Что именно измеряется

Обычные замеры делает C++ runner через `MetricsCollector`. Python отвечает за интерфейс, запуск runner и обработку результатов.

Счётчики относятся к главному потоку программы в пользовательском режиме. В замер входят запуск и загрузка программы. Дополнительные потоки и дочерние процессы в эти счётчики не входят. Кеши перед запуском не очищаются.

Runner можно использовать и без интерфейса:

```bash
./build/runner --cpu 0 --timeout-ms 10000 -- ./build/demo_target 32 4
```

В ответ он выведет JSON с результатом. В примере используется CPU 0 — на вашей машине может потребоваться другой разрешённый CPU.

По сохранённым результатам можно отдельно получить текстовый разбор метрик:

```bash
python3 scripts/analyze.py results/series-*.json
```

```text

```

## Тесты

После сборки:

```bash
ctest --test-dir build --output-on-failure
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

Тесты проверяют сбор метрик, запуск программ, вычисления в демо, анализ результатов и работу интерфейса. Проверка аппаратных циклов CPU может быть пропущена, если счётчик недоступен.
