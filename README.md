# LatencyLab

LatencyLab запускает вашу программу, собирает метрики CPU и помогает найти места, из-за которых она может работать медленно. Всё в терминале: указываете команду, выбираете число запусков и смотрите результат.

Можно начать с готовых примеров — например, сравнить обход массива подряд и с большим шагом или поменять порядок циклов при умножении матриц.

## Что можно посмотреть

- Время выполнения: среднее, минимум и максимум по серии запусков.
- Циклы CPU, инструкции, cache misses, промахи предсказателя ветвлений и другие доступные счётчики.
- Вывод программы и ресурсные показатели, включая page faults.
- Гипотезы о причинах замедления и подсказки, что проверить.
- Топ-5 горячих участков с функцией, файлом, номером строки и фрагментом кода.

При желании можно подключить модель к кнопке **«ИИ-диагноз»** и получить дополнительные объяснения и идеи экспериментов.

## Запуск

Нужны **Linux**, компилятор с поддержкой **C++17** и **Python**. Для первого запуска рекомендуем Python 3.11 или новее — эта версия используется в CI. CMake 3.16+ можно установить через `requirements.txt` вместе с остальными зависимостями.

Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt

cmake -S . -B build -DCMAKE_BUILD_TYPE=RelWithDebInfo
cmake --build build -j2

python3 -m tui --demo --sample 5
```

В интерфейсе уже будет команда для демо. Нажмите **«Запустить»** или замените её своим бинарником с аргументами, например `./my_program --size 1024`.

- **CPU** — один логический процессор для всех запусков. Пустое поле означает первый разрешённый CPU. Сам интерфейс к нему не привязывается.
- **sample** — число отдельных запусков программы. В статистику входят только успешные запуски.
- **Стоп** — завершить текущую программу и остановить серию.

По умолчанию один запуск ограничен 10 секундами. Для долгой задачи добавьте `--timeout 30` при запуске TUI.

Результаты сохраняются в `results/`: `run-*.json` для отдельных запусков и `series-*.json` для сводки серии.

## Готовые эксперименты

Выберите пример в списке над командой или через флаг `--demo`:

| Пример | Имя для `--demo` | Что можно менять |
| --- | --- | --- |
| Массив подряд | `array-sequential` | Размер массива и число проходов |
| Массив с шагом 64 элемента | `array-strided` | Те же параметры для другого порядка чтения |
| Бинарный поиск | `binary-search` | Число элементов и поисковых запросов |
| Матрицы по строкам | `matrix-rows` | Размер матриц и число умножений |
| Матрицы по столбцам | `matrix-columns` | Те же параметры для другого порядка циклов |

Например:

```bash
python3 -m tui --demo matrix-columns --sample 5 --timeout 30
```

Размер задачи редактируется прямо в строке команды. Число проходов внутри программы задаёт работу одного процесса; `sample` определяет, сколько раз запустить этот процесс заново.

[Все команды и параметры демо](docs/demos.md).

## Где именно тратится время

Кнопка **«Участки кода»** открывает отдельный экран профилирования. Выберите **CPU** или **Cache misses** — появятся пять мест с наибольшим числом сэмплов. При выборе строки ниже показывается соответствующий исходник.

Для этого режима дополнительно нужны `perf` и `taskset`. Бинарник должен быть собран с отладочными символами, а исходники — доступны по записанным путям. Сборка `RelWithDebInfo` из инструкции выше уже включает символы.

Это один отдельный запуск: поле `sample` к нему не применяется. Если сэмплов мало, увеличьте объём работы программы. Процент в таблице — доля сэмплов события; считать его точным процентом задержки нельзя. Для cache misses привязка к строке приблизительная.

[Подготовка и ограничения профилирования](docs/hotspots.md).

## ИИ-диагноз

После получения профиля можно нажать **«ИИ-диагноз»**. Модель получит горячие фрагменты кода и, если вы уже выполнили обычную серию, её метрики. В ответ она предложит вероятную причину замедления и несколько экспериментов для проверки.

Поддерживаются DeepSeek, Claude и локальный сервер Ollama. Для внешнего сервиса понадобятся настройка и API-ключ; выбранному провайдеру отправляются код и метрики. Обычный разбор метрик работает без подключения модели.

[Как настроить провайдера](docs/llm.md).

## Если вместо счётчиков прочерки

Часть событий может быть недоступна из-за прав доступа, настроек VM или особенностей CPU. LatencyLab покажет причину и оставит доступные показатели времени и ресурсов.

Если доступ ограничен настройкой `perf_event_paranoid`, можно воспользоваться `scripts/enable_perf.sh`. Скрипт объяснит изменение и запросит подтверждение. Ему нужны права root или sudo; настройка меняется для всей машины до перезагрузки. В контейнере или VM этого может быть недостаточно.

## Что учитывать при замерах

Счётчики собираются для главного потока программы в пользовательском режиме, включая запуск и загрузчик. Дополнительные потоки и дочерние процессы в них не входят. Кеши перед запуском не очищаются.

Разница во времени и гипотеза в интерфейсе ещё не доказывают причину. Сравнивайте одинаковый объём работы и проверяйте предположения отдельными изменениями. Для сравнения серий в TUI есть кнопка **«Запомнить базу»**.

На macOS можно посмотреть интерфейс с явно выбранным моком. Настоящие измерения требуют Linux. [Запуск с моком](tui/README.md#мок-для-просмотра-интерфейса).

## Документация и разработка

Python отвечает за TUI и обработку результатов, C++ runner — за запуск программы и сбор счётчиков через `MetricsCollector`. Профилирование участков кода использует отдельный запуск через perf.

- [Работа с интерфейсом](tui/README.md)
- [Контракт C++ runner](docs/integration.md)
- [Как устроен анализ метрик](docs/cause-analysis.md)

Проверки после сборки:

```bash
ctest --test-dir build --output-on-failure
python3 -m unittest discover -s tests -p 'test_*.py' -v
```

Тесты, которым нужны недоступные счётчики или perf, могут быть пропущены с указанием причины.
